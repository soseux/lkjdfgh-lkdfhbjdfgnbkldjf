# Dota Predictor — основа системы сбора данных

В репозитории реализованы первые четыре этапа плана проекта:

1. PostgreSQL и версионируемые миграции Alembic.
2. Сборщик данных из OpenDota с ограничением частоты запросов.
3. Идемпотентная нормализация профессиональных матчей, команд, игроков и действий драфта.
4. Очередь задач в PostgreSQL на основе `FOR UPDATE SKIP LOCKED`.

Загрузка и разбор реплеев начинаются с пятого этапа и пока намеренно не реализованы.

## Поток данных

```text
OpenDota /proMatches
        │
        ├── неизменяемый JSON → data/raw/opendota/pro_matches/
        │
        └── команды/лиги/серии/матчи → PostgreSQL
                                      │
                              задача fetch_match_details
                                      │
                                      ▼
                         OpenDota /matches/{match_id}
                                      │
        ┌─────────────────────────────┴─────────────────────────┐
        ▼                                                       ▼
data/raw/opendota/matches/                    игроки, участники матчей,
                                             действия драфта, патчи
```

Каждый исходный ответ сохраняется по его SHA-256 и регистрируется в таблице `raw_objects`.
Вместе с ним сохраняются URL источника, время загрузки, размер, HTTP-заголовки и версия
источника. Для записи в базу используются операции upsert, поэтому повторный поиск матчей или
повторная обработка задачи не создают дубликаты матчей и действий драфта.

## Быстрый запуск

Требования:

- Python 3.12 или новее;
- PostgreSQL 15 или новее;
- либо Docker Desktop — приложенный Compose-файл использует PostgreSQL 17.

Создание окружения и установка зависимостей:

```powershell
Copy-Item .env.example .env
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -e ".[dev]"
```

Запуск PostgreSQL через Docker и применение миграций:

```powershell
docker compose up -d postgres
dota-predictor migrate
```

## Сбор матчей

Найти одну страницу последних профессиональных матчей и поставить задачи загрузки их подробных
данных в очередь:

```powershell
dota-predictor discover --pages 1
```

Обработать одну задачу, ограниченное количество задач или запустить worker постоянно:

```powershell
dota-predictor worker --once
dota-predictor worker --max-jobs 100
dota-predictor worker
```

Проверить соединение с базой и текущее количество матчей и задач:

```powershell
dota-predictor status
```

Загрузить подробные данные одного матча напрямую, без очереди:

```powershell
dota-predictor fetch-match 9036960102
```

## Историческая загрузка

Для загрузки старых матчей возьмите значение `next_less_than_match_id` из результата команды
`discover` и передайте его следующему запуску:

```powershell
dota-predictor discover --pages 20 --less-than-match-id 8500000000
```

Параметр `less_than_match_id` позволяет двигаться от новых матчей к старым. В одной странице
OpenDota обычно возвращает до 100 профессиональных матчей.

По умолчанию сборщик делает не более 50 запросов в минуту. Это намеренно консервативное значение
для публичного API. Если у вас есть ключ OpenDota, его можно указать в `.env`:

```dotenv
DOTA_OPENDOTA_API_KEY=ваш_ключ
DOTA_OPENDOTA_REQUESTS_PER_MINUTE=50
```

Повышать лимит следует только в пределах ограничений вашего аккаунта OpenDota.

## Конфигурация

Настройки читаются из переменных окружения или файла `.env` в корне проекта.

| Переменная | Назначение | Значение по умолчанию |
|---|---|---|
| `DOTA_DATABASE_URL` | Строка подключения к PostgreSQL | `postgresql+psycopg://dota:dota@localhost:5432/dota_predictor` |
| `DOTA_OPENDOTA_BASE_URL` | Базовый адрес OpenDota API | `https://api.opendota.com/api` |
| `DOTA_OPENDOTA_API_KEY` | Необязательный ключ OpenDota | пусто |
| `DOTA_OPENDOTA_REQUESTS_PER_MINUTE` | Максимальная частота запросов | `50` |
| `DOTA_HTTP_TIMEOUT_SECONDS` | Тайм-аут HTTP-запроса | `30` |
| `DOTA_RAW_DATA_DIR` | Каталог исходных ответов | `data/raw` |
| `DOTA_WORKER_ID` | Идентификатор обработчика очереди | `local-worker` |
| `DOTA_WORKER_POLL_SECONDS` | Пауза при пустой очереди | `2` |

## Устройство очереди

- Каждая задача уникальна по `dedupe_key`, например `fetch_match_details:123456789`.
- Одновременно можно безопасно запускать несколько worker-процессов.
- Неудачная задача повторяется с экспоненциальной задержкой.
- После пяти неудачных попыток задача получает статус `dead`.
- Блокировки старше 15 минут возвращаются в очередь при запуске постоянного worker-процесса.
- Worker фиксирует получение задачи до выполнения HTTP-запроса.
- Если процесс аварийно завершится, повторная нормализация не создаст дубликаты.

Сейчас поддерживается задача `fetch_match_details`. Загрузка реплеев не выполняется скрытно и
будет добавлена отдельно на следующем этапе проекта.

## Основные таблицы

- `matches` — карты, результаты, стороны, команды, патч и состояние обработки;
- `teams`, `team_aliases` — команды и история их названий;
- `players`, `player_aliases` — игроки и их псевдонимы;
- `series`, `leagues`, `patches` — контекст матча;
- `match_players` — десять участников карты и выбранные ими герои;
- `draft_actions` — упорядоченные пики и баны;
- `raw_objects` — реестр сохранённых исходных ответов;
- `ingestion_jobs` — очередь сбора и обработки данных;
- `team_roster_periods` — подготовленная таблица периодов составов команд.

## Проверка проекта

Запуск автоматических тестов и проверки стиля:

```powershell
pytest
ruff check .
ruff format --check .
```

Тесты не требуют работающей базы данных или доступа к интернету. Для проверки PostgreSQL запустите
базу, примените миграции и выполните:

```powershell
dota-predictor status
```

Проверить генерацию SQL миграции без подключения к базе можно так:

```powershell
alembic upgrade head --sql
```
